# Надёжность системы бронирования

Документ описывает параметры обслуживания (SLI, SLO, MTBF, MTTR, RPO, RTO), механизмы,
которые их обеспечивают, и порядок проверки. Расчётный период: 30 дней (43 200 минут).

## 1. Показатели уровня обслуживания (SLI) и цели (SLO)

**SLI** (Service Level Indicator) — измеряемый показатель качества работы сервиса.
**SLO** (Service Level Objective) — целевое значение SLI.
**SLA** (Service Level Agreement) — обязательство перед клиентом. Для учебной системы
SLA не заключается, ориентируемся на SLO.

| SLI | Как измеряется | SLO (30 дней) |
|---|---|---|
| Доступность API: доля запросов без ошибки 5xx | лог gateway, `scripts/sli-report.sh` | ≥ 99,5 % |
| Задержка API: время ответа gateway (`request_time`) | лог gateway, `scripts/sli-report.sh` | p95 ≤ 300 мс, p99 ≤ 1 с |
| Свежесть уведомлений: задержка от события до обработки | поле `lag=` в логе notifier | 99 % ≤ 60 с |
| Сохранность данных: максимальная потеря данных (RPO) | время последней резервной копии | ≤ 1 ч |
| Время восстановления данных из копии (RTO) | `scripts/restore.sh` выводит время | ≤ 30 мин |

Запросы к `/health` в расчёт доступности не входят: это служебные проверки.

**Бюджет ошибок.** При SLO 99,5 % допустимо 0,5 % неуспешных запросов, то есть около
216 минут полной недоступности в месяц. Бюджет расходуется на сбои и плановые работы
(обновления, миграции). Если бюджет исчерпан, новые функции не выкатываются, пока не
устранены причины сбоев.

**Почему 99,5 %, а не 99,9 %.** Система работает на одном хосте, а восстановление БД из
копии выполняется вручную. Расчёт ниже даёт около 99,98 %, но MTBF пока оценочные, а
перезагрузки хоста и плановые работы реальны. Запас между расчётом и SLO покрывает эти
неопределённости.

## 2. MTBF и MTTR

**MTBF** (Mean Time Between Failures) — среднее время работы между отказами.
**MTTR** (Mean Time To Recovery) — среднее время восстановления после отказа.
Доступность компонента: **A = MTBF / (MTBF + MTTR)**.

MTBF ниже — оценки: истории эксплуатации у системы ещё нет. Для нового кода они взяты
с запасом. В эксплуатации MTBF считается как время работы, делённое на число отказов
(счётчик `RestartCount` контейнера и логи). MTTR — целевые значения; фактические
измеряет `scripts/chaos-test.sh`.

| Компонент | Отказ | MTBF (оценка) | MTTR (цель) | Механизм восстановления | Влияние на клиента |
|---|---|---|---|---|---|
| app (одна реплика) | падение процесса, OOM | 168 ч (раз в неделю) | ≤ 30 с | `restart: unless-stopped` | нет: запросы обслуживает вторая реплика |
| app (обе реплики) | общая ошибка в коде | 720 ч | ≤ 30 с | автоперезапуск | API недоступен |
| apigw (nginx) | падение процесса | 2160 ч | ≤ 10 с | автоперезапуск | API недоступен |
| PostgreSQL | падение процесса | 2160 ч | ≤ 60 с | автоперезапуск, восстановление по WAL | запросы к БД падают |
| PostgreSQL | потеря или порча данных, ошибочный `DROP` | 8760 ч (раз в год) | ≤ 30 мин (RTO) | восстановление из копии | API недоступен, потеря ≤ 1 ч данных |
| Redis | падение процесса | 2160 ч | ≤ 15 с | автоперезапуск | нет: чтение идёт напрямую в БД (медленнее) |
| RabbitMQ | падение процесса | 2160 ч | ≤ 60 с | автоперезапуск, переподключение app | брони создаются, события за время сбоя теряются |
| notifier | падение процесса | 720 ч | ≤ 30 с | fail fast и автоперезапуск | уведомления задерживаются, не теряются |
| pg-backup | копирование перестало работать | 2160 ч | ≤ 1 ч | healthcheck (`unhealthy`), автоперезапуск | нет, но растёт RPO |
| Хост / Docker | перезагрузка, обновление | 720 ч (раз в месяц) | ≤ 5 мин | Docker сам поднимает контейнеры | API недоступен |

### Расчёт доступности API

Критический путь запроса: хост → apigw → app (2 реплики) → PostgreSQL. Redis и RabbitMQ
в него не входят: при их отказе API продолжает отвечать.

| Звено | Доступность | Недоступность за месяц |
|---|---|---|
| Хост | 720 / (720 + 0,083) = 99,988 % | 5,0 мин |
| apigw | 99,99987 % | 4 с |
| app, независимые отказы двух реплик | 1 − (1 − 0,99995)² ≈ 99,9999998 % | < 0,01 с |
| app, общий отказ обеих реплик | 99,9988 % | 30 с |
| PostgreSQL, падение процесса | 99,9992 % | 20 с |
| PostgreSQL, восстановление из копии | 99,994 % | 2,5 мин |
| **Итого (последовательное соединение)** | **≈ 99,98 %** | **≈ 8,4 мин** |

Последовательные звенья перемножаются: A = A₁ · A₂ · … . Параллельные реплики
отказывают одновременно с вероятностью (1 − A)², поэтому вторая реплика app почти
полностью убирает её из расчёта. Это верно только для независимых отказов: ошибка в коде
роняет обе реплики сразу, поэтому общий отказ учтён отдельной строкой.

Итог: расчётные ≈ 8 минут простоя в месяц укладываются в бюджет SLO в 216 минут.

## 3. Отказоустойчивость: как настройки связаны с параметрами

| Настройка | Где | Какой параметр обеспечивает |
|---|---|---|
| `restart: unless-stopped` у всех сервисов | `docker-compose.yml`, `x-reliable` | MTTR в секундах вместо ручного вмешательства |
| Две реплики app за nginx: `max_fails`, `proxy_next_upstream` | `gateway/nginx.conf` | отказ одной реплики не виден клиенту |
| POST не повторяется на другой реплике, если уже дошёл до первой | `proxy_next_upstream` (поведение nginx по умолчанию) | нет двойных броней при сбое |
| Healthcheck с `start_interval: 1s` | все сервисы | быстрое обнаружение готовности, меньше MTTR |
| Переподключение к RabbitMQ с экспоненциальной задержкой (1 → 30 с) | `broker.go`, `KeepAlive` | отказ брокера не роняет API |
| Fail fast в notifier: выход при обрыве связи | `notifier.go` | Docker перезапускает, сообщения ждут в очереди |
| Durable-очередь, persistent-сообщения, ручной ack, `prefetch 10` | `broker.go` | уведомления не теряются при перезапуске |
| Том `rabbitdata` и постоянный `hostname` у RabbitMQ | `docker-compose.yml` | очередь переживает пересоздание контейнера |
| Graceful degradation при отказе Redis | `handlers.go`: промах кэша, чтение из БД | Redis вне критического пути |
| Advisory-блокировка при создании схемы | `db.go`, `migrate` | реплики стартуют одновременно без конфликта |
| `stop_grace_period` | app 15 с, postgres 30 с | корректное завершение без потери запросов и данных |
| Ротация логов (10 МБ × 3) | `x-reliable` | переполнение диска логами не уронит хост |
| Файрвол применяется при каждом старте контейнера, fail-closed | `firewall/entry.sh` | автоперезапуск не открывает сеть |

**Почему файрвол встроен в контейнеры.** В ДЗ 4 правила ставил отдельный
sidecar-контейнер. При автоперезапуске Docker создаёт контейнеру новое сетевое
пространство, и правила sidecar в нём уже не действуют. Перезапущенный сервис работал бы
без файрвола (fail-open). Теперь `firewall/entry.sh` применяет правила перед запуском
сервиса при каждом старте. Если правила применить не удалось, сервис не запускается
(fail-closed). После этого процесс теряет `NET_ADMIN`, поэтому взломанный сервис не
сможет отключить собственный файрвол.

## 4. Резервное копирование БД

| Параметр | Значение |
|---|---|
| Метод | логический дамп `pg_dump`, формат custom, сжатие |
| Расписание | при старте, затем каждые `BACKUP_INTERVAL` = 3600 с |
| RPO | ≤ 1 ч |
| Хранение | 48 последних копий (2 суток), папка `./backups` на хосте |
| Проверка при создании | `pg_restore --list` (дамп читается) и контрольная сумма SHA-256 |
| Мониторинг | healthcheck `pg-backup` становится `unhealthy`, если нет копии свежее двух интервалов |
| Права доступа | `umask 077`: копии содержат персональные данные |
| Сеть | `pg-backup` ходит только в PostgreSQL, Redis и RabbitMQ запрещены файрволом |
| RTO | ≤ 30 мин; фактическое время выводит `scripts/restore.sh` |

Копии лежат в папке на хосте, а не в docker volume, поэтому они переживают
`docker compose down -v`.

**Проверка восстановления.** Бэкап, из которого ни разу не восстанавливали, нельзя
считать бэкапом. `scripts/restore.sh <файл>` разворачивает копию в отдельную БД
`restore_check` и выводит число строк. Рабочие данные при этом не затрагиваются.

**Восстановление рабочей БД:**

```bash
docker compose stop app-1 app-2           # остановить запись
./scripts/restore.sh                      # выбрать копию
./scripts/restore.sh slotdb_20261114T180000Z.dump slotdb
docker compose start app-1 app-2
docker compose exec redis sh -c 'redis-cli -a "$REDIS_PASSWORD" FLUSHALL'   # сбросить устаревший кэш
```

## 5. Известные ограничения и развитие

| Ограничение | Решение в промышленной системе |
|---|---|
| PostgreSQL в одном экземпляре (единая точка отказа) | потоковая репликация и автоматическое переключение (Patroni) |
| RPO 1 ч: логический дамп | архивирование WAL (wal-g, pgBackRest), восстановление на момент времени, RPO в минутах |
| Копии на том же хосте | правило 3-2-1: копия на другом носителе и вне площадки, шифрование (age или gpg) |
| События за время отказа RabbitMQ теряются | паттерн transactional outbox: событие пишется в БД в одной транзакции с бронью |
| RabbitMQ и Redis в одном экземпляре | кластер RabbitMQ из 3 узлов с quorum-очередями, Redis Sentinel |
| Один хост | несколько узлов, оркестратор (Kubernetes) |
| Docker не перезапускает `unhealthy` контейнеры | в Kubernetes это делает liveness probe; здесь сервисы сами выходят при неустранимой ошибке |
